# 架构说明

## 总览

```
 Web (Next.js)   桌面 (Tauri 2, 内嵌 Web 静态导出)   移动 (Expo)
        \                  |                           /
         \______ @ainative/api-client（OpenAPI 生成 + SSE + SignalR）______/
                                   |
                      ASP.NET Core API（.NET 10）  ←──  MCP 客户端（Claude Code 等）经 /mcp 接入
        HTTP 控制器 · SignalR 实时通道 · MCP 服务 · JWT / API 密钥认证 · ProblemDetails
                                   |
                 Application：命令/查询管道 · 权限 · 模块 · 平台动作
                 智能体运行时 · 工作流 · 对话 · 审批 · 知识与记忆 · 实时变更
                                   |
     Infrastructure：EF Core + PostgreSQL · 唤醒队列 · 心跳调度器 · 工作流引擎 · 模型网关 · 向量化与混合检索
                                   |
                PostgreSQL 17（pgvector）       模型：Claude / OpenAI 兼容 / 演示
```

三端只依赖后端生成的 TypeScript 客户端，接口形状由 OpenAPI 文档唯一决定。

## 多租户、身份与权限

- 一个 **用户** 可以通过 **成员关系** 加入多个 **空间（租户）**。登录得到的 JWT 携带用户、租户和成员关系；切换空间会换发新令牌。
- 每次请求解析成员关系，得到当前租户、操作者（人或智能体）和功能权限集合，放进 `ITenantContext`。成员被停用后令牌立即失效。
- 所有 `ITenantScoped` 实体有全局查询过滤器，只能读到当前租户的数据；保存时自动补租户，并拒绝跨租户写入。
- 权限是 **功能键**（如 `tasks.manage`），角色是功能键的集合，支持 `tasks.*` 和 `*` 通配。请求类型上用 `[RequireFeature]` 声明，管道统一检查，同时要求功能所属模块在当前空间已启用。
- 智能体也是操作者：它的权限是自己配置的功能集合，不会因为是谁唤醒它而放大。
- **个人 API 密钥**（`ank_` 开头）给 MCP 客户端和脚本用：只存 SHA-256，按明文前缀查找后定长比较。密钥以所属成员的身份执行，权限是成员当前权限与密钥范围的交集（只读密钥只含 `*.view`）；成员被停用、密钥吊销或过期立即失效。API 密钥不能用来查看、创建或吊销密钥。

## 请求管道

控制器把 HTTP 请求转换为命令或查询，交给调度器。管道顺序：

1. **权限**：登录空间、功能权限、模块启用。
2. **校验**：FluentValidation，失败返回 400 和字段错误。
3. **日志**：慢请求告警。
4. **事务**：只包写操作。处理器结束后统一保存并提交，提交成功才执行登记的后续动作（实时推送、唤醒信号），失败则全部回滚。

错误统一为 ProblemDetails，附带机器可读的 `code`（如 `approval.already_decided`），前端直接展示中文 `title`。

## 模块与平台动作

- **模块**声明自己的功能权限，可按空间启用或停用；核心模块不可停用。
- **平台动作**是一次定义、多处使用的业务操作：界面（`/api/actions`）、智能体工具调用、对话中的模型调用走同一个入口。输入类型自动生成 JSON Schema 给模型；入口统一做权限检查和审批判断，动作在独立的依赖注入作用域里执行。
- 现有动作：`tasks.list/get/create/update_status/assign/comment`，`agents.list_team/wake/hire`，`knowledge.search/get_document/create_document`，`memory.retain/recall/forget`，`workflows.list/list_events/get/create/update/run/get_run`。`agents.hire`、`workflows.create/update` 对智能体要求人工审批。
- 模块还可以声明自己发布的**平台事件**（`PlatformEventDefinition`，附载荷字段说明），供工作流订阅，见下文。
- 新模块和动作按约定自动注册，外部程序集用 `AddPlatformModuleAssembly` 接入。

## 智能体运行时

智能体是"有岗位的 AI 员工"：岗位说明（系统提示词）、汇报对象、模型、权限、需审批的动作、月度预算和心跳周期。

### 唤醒

被指派任务、任务有新评论、审批有结论、同事委派、手动唤醒、定时心跳，都会向 **唤醒队列** 投递一条唤醒。每个智能体最多只有一条排队中的唤醒：新唤醒通过 `INSERT ... ON CONFLICT` 合并进去（原因列表追加、计数加一），并用幂等键去重，避免短时间内重复执行。

### 调度

后台的 **心跳调度器**：

- 用 `FOR UPDATE SKIP LOCKED` 批量领取排队中的唤醒，按并发上限创建执行；同一智能体用 advisory lock 串行化。
- 唤醒入队后通过进程内信号立即触发调度，平时按轮询间隔兜底；另有定时扫描为到期的智能体投递心跳唤醒。
- 启动时把上次异常中断的执行标记为失败、把卡在"工作中"的智能体复位、把已领取未完成的唤醒放回队列（当前假设单实例部署）。

### 执行

一次执行就是一个有步数上限的工具调用循环：

1. 组装提示词：岗位说明、团队、唤醒原因、关注的任务，以及按本轮内容自动回忆的相关记忆和知识库片段（有相应权限时）。
2. 调用模型（流式），逐字增量通过 SignalR 推给正在查看的客户端，完整的回复、工具调用和结果作为 **执行事件** 落库。
3. 工具调用经平台动作入口执行；需要审批的动作生成审批单后返回"待审批"，审批有结论时智能体再次被唤醒。审批结论先以条件更新落定（保证动作最多执行一次），再执行动作并写回结果；如果进程在两者之间中断，调度器会把这类审批标记为"结果未知"并唤醒申请人核实，而不是盲目重跑。
4. 结束时记录 token 用量与花费、释放任务领取锁；超出预算会自动暂停智能体。执行期间被人暂停或终止的状态不会被覆盖。

任务的 **领取（checkout）** 是带状态条件的原子更新，并带租约，防止两个执行同时处理一个任务，也防止崩溃的执行永久占用任务。

## 工作流与自动化

工作流把固定流程交给平台执行：一个触发器加一串按顺序执行的步骤（定义存在 `workflows`，步骤为 jsonb）。

- **触发**：手动（界面、对话或 `workflows.run`）；平台事件（如 `tasks.status_changed`，可加过滤条件 `trigger.to == 'done'`）；定时（5 段 cron + IANA 时区，夏令时跳过的时刻顺延到切换后的第一分钟，重复的时刻按第一次出现计算）。
- **步骤**：`action` 执行平台动作；`agent_task` 建任务派给智能体，可以等它完成并取它写在评论里的结论；`llm` 让模型处理文本，输出是 JSON 时可以直接取字段；`delay` 等待。每步可以设执行条件 `when` 和"失败也继续"。
- **表达式与模板**：字符串里写 `{{ 表达式 }}`，引用 `trigger`、`input`、`steps.<key>.output`；整个值只有一个表达式时保留原始 JSON 类型（数字、对象不会变成字符串）。表达式是自带的小语言（路径、比较、`&& || !`、`contains`、`length/lower/upper/trim/json/default`），保存时做语法校验，不执行任意代码。
- **运行身份**：工作流以**最后保存它的操作者**（成员或智能体）的身份和当前权限运行。保存时校验引用的动作、事件、智能体都在保存者的权限之内，所以改一个别人建的工作流不能借用对方的权限。智能体保存的工作流遇到需审批的动作会进入等待，审批单关联到这次运行，审批结论由工作流接着处理，不再唤醒智能体。
- **事件**：业务写操作在自己的事务里调用 `IPlatformEvents.PublishAsync`（载荷按需惰性构造），订阅它的工作流运行与业务变化一起提交；没有订阅时只多一两次索引查询，不构造载荷。每次触发都按所有者当前的权限复查事件所需权限，被收回权限、离开空间或被停用的所有者不再收到载荷。同一工作流的触发与删除串行（`workflow-trigger:{id}` advisory lock），频率计数与新建运行是原子的。
- **执行引擎**：后台 `WorkflowEngine` 用 `FOR UPDATE SKIP LOCKED` 领取排队中或等待到期的运行，每次推进一步，按运行所有者的身份和权限执行。动作的副作用与"步骤完成"在同一事务提交；所有状态推进都是带 `status = running AND current_step = n` 条件的更新，与取消、删除并发时由条件更新决定胜负，落败的一方整体回滚，动作不会执行两次。等待审批、等待任务完成和延时都是"等待中"状态，由对应事件或到期时间唤醒；登记等待与事件唤醒在同一把 advisory lock 下判断，不会错过唤醒。审批已通过、动作仍在执行时拒绝取消运行，避免动作结果无人接手；审批发起的动作带着所属运行的上下文执行，防自触发同样生效。进程启动时，以及执行意外崩溃后的定期巡检中，把没人执行的 Running 运行放回队列，连续崩溃 3 次的标记为失败。
- **防失控**：工作流自己的步骤引发的事件不会再触发它自己；嵌套触发深度上限 3；每个工作流每分钟最多被事件触发 30 次（均可配置）。运行保存启动时的定义快照，修改工作流不影响已开始的运行；编辑带 `expectedUpdatedAt` 检测冲突（界面总会带上，`workflows.update` 动作必填），推进定时的下一次时间不算编辑。

## 客户管理（CRM）

第一个业务模块，用来验证"模块 + 动作 + 事件"这套扩展方式能否承载真实业务。模块键 `crm`，权限 `crm.view`、`crm.manage`、`crm.configure`（配置销售阶段）；内置"成员"可管理、"只读"可查看，首席助理默认可管理。

- **数据**：客户（公司或组织）、联系人（可挂在客户下，也可以单独作为个人客户）、商机、销售阶段、跟进记录。客户、联系人、商机都有负责人（本空间成员）和标签；记录在空间内全员可见，暂不按负责人隔离数据。
- **销售阶段**：每个空间一套可配置的阶段（新空间自带"线索→需求确认→方案报价→商务谈判→赢单/输单"），阶段有成交概率和类型（进行中 / 赢单 / 输单）。商机的状态由所在阶段的类型决定，结束时记下结束时间、重新打开时清除；修改阶段类型会同步其中商机的状态。仍有商机的阶段不能删除。阶段整体保存，在 `crm-stages:{tenant}` advisory lock 下串行。
- **推进商机**：以"阶段仍是读到的那个"为条件先锁住商机（条件更新），并发的另一次推进返回 409 而不是悄悄覆盖；每次推进自动写一条"阶段变化"跟进记录（不能删除），并发布 `crm.deal_stage_changed`。编辑客户、联系人、商机都带 `expectedUpdatedAt` 检测冲突。
- **跟进记录**：电话、会议、邮件、备注，至少关联客户、联系人、商机中的一个；只关联商机或联系人时自动补上其所属客户，所以客户页能看到名下全部往来。客户、联系人、商机的"最近往来时间"是冗余字段，记录跟进时用条件更新刷新，不算编辑，不影响冲突检测。
- **销售看板**：按阶段分列商机；进行中金额、按概率加权的预测金额、本月赢单金额按货币分别合计（不做汇率换算）；赢单、输单列只含最近 30 天结束的商机。合计在数据库里分组聚合，卡片数量有上限。
- **搜索**：名称、邮箱、电话等用 `ILIKE` 包含匹配，`pg_trgm` 的 GIN 索引让包含匹配也能走索引。应用层通过 `ITextMatcher` 表达"包含"，PostgreSQL 实现负责转义通配符并显式指定转义符，Application 层不依赖 Npgsql。
- **动作**（供对话、智能体、工作流、MCP 使用）：`crm.search`、`crm.get_company`、`crm.get_contact`、`crm.get_deal`、`crm.list_deals`、`crm.get_pipeline`、`crm.create_company`、`crm.update_company`、`crm.create_contact`、`crm.update_contact`、`crm.create_deal`、`crm.update_deal`、`crm.move_deal`、`crm.log_activity`。阶段按名称指定，找不到时错误里列出可选阶段；修改类动作只需传要改的字段，内部先读当前版本再带版本号提交。
- **事件**：`crm.company_created`、`crm.contact_created`、`crm.deal_created`、`crm.deal_stage_changed`、`crm.activity_logged`，例如"商机赢单（`trigger.to.kind == 'won'`）后自动建交付任务派给智能体"。
- **新空间初始化**：模块可以实现 `ITenantInitializer`，注册新空间时在同一事务里执行（CRM 用它写入默认阶段）；已有空间由迁移补齐。

## 对话

对话是用户与平台的直接入口：用户消息和模型回复（含工具调用与结果）按序存储在 `conversation_messages`（jsonb）。每一轮在当前用户的身份与权限下调用平台动作，所以对话里能做的事和界面上完全一致。客户端可以用 SSE（`POST /api/conversations/{id}/messages`）或 SignalR 的 `StreamChat` 接收流式事件。

同一对话同时只跑一轮（PostgreSQL advisory lock，跨实例生效），上一轮没结束时新消息返回 `conversation.busy`。带给模型的历史是最近 60 条且不超过约 12 万字符，并从一条用户消息开始，长对话不会撑爆上下文窗口。

## 知识与记忆

- **文档** 保存时同步切成片段（按段落累积，超长段落按句子切，每段带上 Markdown 标题路径，相邻片段少量重叠），立即可以按关键词检索；**记忆** 是一条条短事实，各自是一个片段。两者存在同一张 `knowledge_chunks` 表里，检索一次覆盖。
- **关键词检索** 不依赖数据库分词插件：应用内分词（中日韩文字切成二元组，其他文字按词，全角折叠为半角），存成生成列 `tsvector` + GIN 索引。
- **向量检索**：后台索引器批量向量化新片段，写入 `vector(1024)` 列（HNSW 余弦索引）。任何模型的输出都统一到 1024 维（补零或按 Matryoshka 截断，再归一化）；更换模型后旧向量自动逐批重建。没有配置向量模型时用离线演示向量（特征哈希）。
- **混合排序**：向量近邻与关键词各取候选，按倒数排名融合（RRF，k = 60）；向量候选有距离门槛，过滤掉不相关的近邻。HNSW 开启迭代扫描，带过滤条件时也能凑满候选。
- **可见性**：文档全空间可见；记忆分共享、成员私有、智能体私有，检索时按当前操作者过滤，`memory.manage` 可以查看全部。原生 SQL 绕过了 EF 过滤器，所以租户和可见性条件在检索 SQL 里显式写出。
- 同一归属下内容相同的记忆只保留一条；智能体记下的记忆会关联到当时的执行和任务，便于追溯。

## MCP 服务

`/mcp` 是无状态的 Streamable HTTP MCP 服务（官方 `ModelContextProtocol.AspNetCore`）。工具列表就是当前身份可用的平台动作，调用走同一个动作入口，所以权限、模块启用和审批规则与界面完全一致（调用者是密钥所属的成员）。鉴权和 REST 接口相同（登录令牌或 API 密钥），查询类动作标注为只读工具。

## 实时通道

写操作提交后发布 **实体变更**（agent、work_item、run、approval、conversation、module、knowledge_document、memory、workflow、workflow_run），SignalR 按租户分组推送；客户端据此让对应查询失效重取，三端都不轮询。查看某次执行时可订阅该执行的分组，接收逐字输出和新事件；客户端会在断线重连后自动重新订阅，并把当前查询全部重取一次补上断线期间的变化。连接的启动与断开按调用顺序串行执行（切换空间时不会卡在断开中），首次连接失败会按退避节奏继续重试。

编辑类接口带上读取时的 `updatedAt`（例如 `UpdateWorkItemRequest.expectedUpdatedAt`），期间被别人或智能体改过就返回 409，而不是用旧数据覆盖。成员被停用、移除或角色权限变化后，本实例的权限缓存在提交后立即清除。

## 模型网关

所有模型统一为 `Microsoft.Extensions.AI` 的 `IChatClient`：

- `anthropic`：官方 Anthropic .NET SDK，默认模型 `claude-opus-5-5`。
- `openai`：OpenAI 及任何兼容端点（`BaseUrl` 指向即可，如本地 Ollama）。
- `demo`：未配置密钥时的内置演示模型，会按真实流程调用工具，便于本地体验和测试。

客户端按（供应商, 模型）缓存；花费按内置价格表或配置的 `Ai:Pricing` 估算。

## 客户端

- **Web**：Next.js App Router + shadcn/ui；TanStack Query 管理服务端状态，查询键集中定义，实时变更映射到查询失效。可通过 `NEXT_OUTPUT=export` 静态导出。
- **桌面**：Tauri 2 只做原生外壳，加载 Web 静态导出；单实例、窗口状态记忆、外链用系统浏览器打开；CSP 限制脚本只能来自应用本身。
- **移动**：Expo Router；令牌存系统安全存储；对话用 `expo/fetch` 读流，任务与审批通过 SignalR 实时刷新；知识页可以检索文档和记忆；“我的”里可以查看、启停和手动运行工作流；“客户”页可以查商机、客户和联系人，一键拨号或发邮件，推进商机、随手记录跟进。
- 三端共用 `@ainative/api-client` 里的 `sessionCan`，按与后端相同的通配规则决定显示哪些入口。

## 测试

- 单元测试：领域不变量（含商机状态与结束时间）、权限通配、JSON 约定、动作工具集、模型网关、分词与切分、向量归一化、API 密钥格式、工作流表达式与模板、cron 计算（含夏令时）。
- 集成测试：真实 PostgreSQL（Testcontainers 或已有实例），覆盖注册登录、租户隔离、角色权限、成员停用即时生效、模块停用、智能体评论执行、唤醒合并、招聘审批与中断恢复、预算暂停、任务领取冲突、编辑冲突、对话串行与历史上限、实时通道、知识库检索与隔离、记忆可见性、智能体自动回忆、API 密钥、MCP 客户端调用，以及工作流的手动运行与模板、事件过滤、等待智能体完成、智能体所有的工作流走审批、取消运行驳回审批并发出审批结论事件、动作执行中拒绝取消、所有者失去事件权限后不再触发、崩溃运行的补跑、防自触发、定时触发、延时、版本冲突、定义校验、权限与租户隔离；客户管理的阶段推进与看板合计、阶段配置（占用保护、类型同步）、编辑冲突、角色与模块权限、租户隔离、通配符搜索、删除时的关联处理、赢单触发工作流、按名称操作的动作。
- 每个集成测试用独立数据库，结束时清空连接池并删库，避免并行时连接数耗尽。

## 后续方向

- 知识库进阶：PDF/Word 等文件解析、按文档权限过滤、重排序模型、记忆整理（合并、过期）。
- 接入外部 MCP 服务：让智能体调用外部 MCP 工具。
- 工作流进阶：分支与并行、循环处理列表、外部 Webhook 触发、可视化编排，以及更多模块发布事件。
- 业务模块：项目管理、分析报表等继续作为可启用的模块接入；CRM 进阶：按负责人或部门的数据权限、自定义字段、导入导出、报价与合同。
- 多实例部署：调度器的领导者选举或分布式领取，Redis 背板的 SignalR。
