# 架构说明

## 总览

```
 Web (Next.js)   桌面 (Tauri 2, 内嵌 Web 静态导出)   移动 (Expo)
        \                  |                           /
         \______ @ainative/api-client（OpenAPI 生成 + SSE + SignalR）______/
                                   |
                      ASP.NET Core API（.NET 10）  ←──  MCP 客户端（Claude Code 等）经 /mcp 接入
        HTTP 控制器 · SignalR 实时通道 · MCP 服务 · JWT / API 密钥认证 · ProblemDetails
                                   |
                 Application：命令/查询管道 · 权限 · 模块 · 平台动作
                 智能体运行时 · 工作流 · 对话 · 审批 · 知识与记忆 · 实时变更
                                   |
     Infrastructure：EF Core + PostgreSQL · 唤醒队列 · 心跳调度器 · 工作流引擎 · 模型网关 · 向量化与混合检索
                                   |
                PostgreSQL 17（pgvector）       模型：Claude / OpenAI 兼容 / 演示
```

三端只依赖后端生成的 TypeScript 客户端，接口形状由 OpenAPI 文档唯一决定。

## 多租户、身份与权限

- 一个 **用户** 可以通过 **成员关系** 加入多个 **空间（租户）**。登录得到的 JWT 携带用户、租户和成员关系；切换空间会换发新令牌。
- 每次请求解析成员关系，得到当前租户、操作者（人或智能体）和功能权限集合，放进 `ITenantContext`。成员被停用后令牌立即失效。
- 所有 `ITenantScoped` 实体有全局查询过滤器，只能读到当前租户的数据；保存时自动补租户，并拒绝跨租户写入。
- 权限是 **功能键**（如 `tasks.manage`），角色是功能键的集合，支持 `tasks.*` 和 `*` 通配。请求类型上用 `[RequireFeature]` 声明，管道统一检查，同时要求功能所属模块在当前空间已启用。
- 智能体也是操作者：它的权限是自己配置的功能集合，不会因为是谁唤醒它而放大。
- **个人 API 密钥**（`ank_` 开头）给 MCP 客户端和脚本用：只存 SHA-256，按明文前缀查找后定长比较。密钥以所属成员的身份执行，权限是成员当前权限与密钥范围的交集（只读密钥只含 `*.view`）；成员被停用、密钥吊销或过期立即失效。API 密钥不能用来查看、创建或吊销密钥。

## 请求管道

控制器把 HTTP 请求转换为命令或查询，交给调度器。管道顺序：

1. **权限**：登录空间、功能权限、模块启用。
2. **校验**：FluentValidation，失败返回 400 和字段错误。
3. **日志**：慢请求告警。
4. **事务**：只包写操作。处理器结束后统一保存并提交，提交成功才执行登记的后续动作（实时推送、唤醒信号），失败则全部回滚。

错误统一为 ProblemDetails，附带机器可读的 `code`（如 `approval.already_decided`），前端直接展示中文 `title`。请求日志放在异常处理之外，记录的是最终状态码；客户端中途断开的请求记为 499 而不是 500。启动时自动迁移会先建好迁移历史表，空库首次启动不会出现查询失败的错误日志。

## 模块与平台动作

- **模块**声明自己的功能权限，可按空间启用或停用；核心模块不可停用。模块可以声明依赖的其他模块，依赖没启用时它也不生效（见进销存）。
- **平台动作**是一次定义、多处使用的业务操作：界面（`/api/actions`）、智能体工具调用、对话中的模型调用走同一个入口。输入类型自动生成 JSON Schema 给模型；入口统一做权限检查和审批判断，动作在独立的依赖注入作用域里执行。
- 现有动作：`tasks.list/get/create/schedule/update_status/assign/comment`，`agents.list_team/wake/hire`，`knowledge.search/get_document/create_document`，`memory.retain/recall/forget`，`workflows.list/list_events/get/create/update/run/get_run`。`agents.hire`、`workflows.create/update` 对智能体要求人工审批。
- 模块还可以声明自己发布的**平台事件**（`PlatformEventDefinition`，附载荷字段说明），供工作流订阅，见下文。
- 新模块和动作按约定自动注册，外部程序集用 `AddPlatformModuleAssembly` 接入。
- 除了编译期定义的动作，**动态动作来源**（`IDynamicActionSource`）可以在运行时按空间提供动作，输入 Schema 由来源直接给出（目前是外部 MCP 服务的工具，见「集成」）。动作入口按 `GetAllAsync` / `FindAsync` 合并两类动作，智能体、对话、工作流和界面看到的是同一份列表，权限、模块启用与审批判断也相同。

## 智能体运行时

智能体是"有岗位的 AI 员工"：岗位说明（系统提示词）、汇报对象、模型、权限、需审批的动作、月度预算和心跳周期。

### 唤醒

被指派任务、任务有新评论、审批有结论、同事委派、前置任务关闭、手动唤醒、定时心跳，都会向 **唤醒队列** 投递一条唤醒。每个智能体最多只有一条排队中的唤醒：新唤醒通过 `INSERT ... ON CONFLICT` 合并进去（原因列表追加、计数加一），并用幂等键去重，避免短时间内重复执行。

### 调度

后台的 **心跳调度器**：

- 用 `FOR UPDATE SKIP LOCKED` 批量领取排队中的唤醒，按并发上限创建执行；同一智能体用 advisory lock 串行化。
- 唤醒入队后通过进程内信号立即触发调度，平时按轮询间隔兜底；另有定时扫描为到期的智能体投递心跳唤醒。
- 启动时把上次异常中断的执行标记为失败、把卡在"工作中"的智能体复位、把已领取未完成的唤醒放回队列（当前假设单实例部署）。

### 执行

一次执行就是一个有步数上限的工具调用循环：

1. 组装提示词：岗位说明、团队、唤醒原因、关注的任务，以及按本轮内容自动回忆的相关记忆和知识库片段（有相应权限时）。
2. 调用模型（流式），逐字增量通过 SignalR 推给正在查看的客户端，完整的回复、工具调用和结果作为 **执行事件** 落库。
3. 工具调用经平台动作入口执行；需要审批的动作生成审批单后返回"待审批"，审批有结论时智能体再次被唤醒。审批结论先以条件更新落定（保证动作最多执行一次），再执行动作并写回结果；如果进程在两者之间中断，调度器会把这类审批标记为"结果未知"并唤醒申请人核实，而不是盲目重跑。
4. 结束时记录 token 用量与花费、释放任务领取锁；超出预算会自动暂停智能体。执行期间被人暂停或终止的状态不会被覆盖。

任务的 **领取（checkout）** 是带状态条件的原子更新，并带租约，防止两个执行同时处理一个任务，也防止崩溃的执行永久占用任务。

## 工作流与自动化

工作流把固定流程交给平台执行：一个触发器加一串按顺序执行的步骤（定义存在 `workflows`，步骤为 jsonb）。步骤可以嵌套：条件分支和遍历里再放步骤，最多 3 层，整个工作流最多 50 步，步骤标识在整个工作流里唯一。

- **触发**：手动（界面、对话或 `workflows.run`）；平台事件（如 `tasks.status_changed`，可加过滤条件 `trigger.to == 'done'`）；定时（5 段 cron + IANA 时区，夏令时跳过的时刻顺延到切换后的第一分钟，重复的时刻按第一次出现计算）；Webhook（见下）。
- **步骤**：`action` 执行平台动作；`agent_task` 建任务派给智能体，可以等它完成并取它写在评论里的结论；`llm` 让模型处理文本，输出是 JSON 时可以直接取字段；`delay` 等待；`http` 调用外部接口；`branch` 按顺序判断各分支条件，执行第一个成立的分支（最后一个分支可以不写条件，表示其他情况）；`for_each` 对列表的每一项执行一组子步骤。每步可以设执行条件 `when` 和"失败也继续"；子步骤失败且不允许继续时整个运行失败，所在的分支或遍历一并标记失败。
- **表达式与模板**：字符串里写 `{{ 表达式 }}`，引用 `trigger`、`input`、`steps.<key>.output`，遍历里另有 `item`（当前项）和 `index`（序号）；整个值只有一个表达式时保留原始 JSON 类型（数字、对象不会变成字符串）。表达式是自带的小语言（路径、比较、`&& || !`、`contains`、`length/lower/upper/trim/json/default`），保存时做语法校验，不执行任意代码。
- **运行身份**：工作流以**最后保存它的操作者**（成员或智能体）的身份和当前权限运行。保存时校验引用的动作、事件、智能体都在保存者的权限之内，所以改一个别人建的工作流不能借用对方的权限。智能体保存的工作流遇到需审批的动作会进入等待，审批单关联到这次运行，审批结论由工作流接着处理，不再唤醒智能体。
- **事件**：业务写操作在自己的事务里调用 `IPlatformEvents.PublishAsync`（载荷按需惰性构造），订阅它的工作流运行与业务变化一起提交；没有订阅时只多一两次索引查询，不构造载荷。每次触发都按所有者当前的权限复查事件所需权限，被收回权限、离开空间或被停用的所有者不再收到载荷。同一工作流的触发与删除串行（`workflow-trigger:{id}` advisory lock），频率计数与新建运行是原子的。
- **分支与遍历的执行**：每个步骤一条运行记录，用路径区分位置（顶层是序号 `2`，分支或遍历里是 `2.<分支序号或第几项>.<子步骤序号>`），`(run_id, path)` 唯一。只有顶层步骤完成才推进 `current_step`，子步骤的状态写入仍以"停在这个顶层步骤"为条件，所以取消、删除的并发处理与顶层步骤相同。分支选中哪一支、遍历的列表快照在开始时写进控制步骤的输入；等待之后重新执行时，已完成的子步骤按记录重放（输出重新放回上下文），不再执行，分支不重新判断，遍历也不重新求值列表。遍历输出 `count` 和 `results`（每一项最后一个实际执行的子步骤的输出），单次最多 `Workflows:MaxLoopItems`（默认 100）项。
- **HTTP 请求**：地址、请求头和请求体都可以写模板；对象和数组按 JSON 发送，单个字符串按纯文本发送；返回 JSON 时自动解析，后续步骤可以按字段引用，非 2xx 视为失败但保留输出。出站客户端整个进程共用一个连接池，超时默认 30 秒、最长 120 秒，响应最大 1 MB，支持 GBK 等常见编码。为防止借工作流探测内网，每次建立连接时检查实际要连接的 IP，默认拒绝本机、私有网段、链路本地（含云厂商元数据地址）、运营商级 NAT 和组播地址，重定向和解析到内网的域名同样被挡住；不走系统代理，否则只能检查代理本身的地址。这套出站规则与外部 MCP 服务共用，确实需要调用同一内网的服务时设置 `OutboundNetwork:AllowPrivateNetworkRequests=true`。请求头里可以写 `{{ secrets.名称 }}` 引用空间密钥（见「集成」），运行记录里保存的是引用写法而不是明文；其余 Authorization、Cookie 以及名称含 token / key / secret / password 的请求头打码；HTTP 请求无法随事务回滚，进程在请求发出后、结果提交前崩溃时会重发。
- **Webhook**：选择 Webhook 触发时生成 32 字节随机令牌，地址为 `POST /api/hooks/workflows/{令牌}`，不需要登录，令牌本身就是凭证，只返回给有 `workflows.manage` 的成员，可以重新生成让旧地址失效，改成别的触发方式时作废。收到请求时按令牌跨空间找到工作流（部分唯一索引），进入它所在的空间、按系统身份创建运行，步骤仍以工作流所有者的身份执行。请求体（JSON、表单或文本，最大 256 KB）、查询参数和请求头（名称小写，去掉 Authorization、Cookie）放进 `trigger.body`、`trigger.query`、`trigger.headers`，可以加过滤条件；成功返回 202 和运行 ID，过滤不通过时 `started` 为 false。令牌不存在、工作流停用或模块未启用时返回 404，超过每分钟次数上限返回 429。与事件触发一样持有 `workflow-trigger:{id}` 锁，频率计数和新建运行是原子的。
- **执行引擎**：后台 `WorkflowEngine` 用 `FOR UPDATE SKIP LOCKED` 领取排队中或等待到期的运行，每次推进一步，按运行所有者的身份和权限执行。动作的副作用与"步骤完成"在同一事务提交；所有状态推进都是带 `status = running AND current_step = n` 条件的更新，与取消、删除并发时由条件更新决定胜负，落败的一方整体回滚，动作不会执行两次。等待审批、等待任务完成和延时都是"等待中"状态，由对应事件或到期时间唤醒；登记等待与事件唤醒在同一把 advisory lock 下判断，不会错过唤醒。审批已通过、动作仍在执行时拒绝取消运行，避免动作结果无人接手；审批发起的动作带着所属运行的上下文执行，防自触发同样生效。进程启动时，以及执行意外崩溃后的定期巡检中，把没人执行的 Running 运行放回队列，连续崩溃 3 次的标记为失败。
- **防失控**：工作流自己的步骤引发的事件不会再触发它自己；嵌套触发深度上限 3；每个工作流每分钟最多被事件触发 30 次，Webhook 同样每分钟最多 30 次（均可配置）。运行保存启动时的定义快照，修改工作流不影响已开始的运行；编辑带 `expectedUpdatedAt` 检测冲突（界面总会带上，`workflows.update` 动作必填），推进定时的下一次时间不算编辑。

## 客户管理（CRM）

第一个业务模块，用来验证"模块 + 动作 + 事件"这套扩展方式能否承载真实业务。模块键 `crm`，权限 `crm.view`、`crm.manage`（含导入）、`crm.configure`（配置销售阶段和自定义字段）；内置"成员"可管理、"只读"可查看，首席助理默认可管理。

- **数据**：客户（公司或组织）、联系人（可挂在客户下，也可以单独作为个人客户）、商机、销售阶段、跟进记录。客户、联系人、商机都有负责人（本空间成员）和标签；记录在空间内全员可见，暂不按负责人隔离数据。
- **销售阶段**：每个空间一套可配置的阶段（新空间自带"线索→需求确认→方案报价→商务谈判→赢单/输单"），阶段有成交概率和类型（进行中 / 赢单 / 输单）。商机的状态由所在阶段的类型决定，结束时记下结束时间、重新打开时清除。仍有商机的阶段不能删除，也不能改类型（商机的状态、结束时间、阶段变化记录和事件只随推进产生）。阶段整体保存，在 `crm-stages:{tenant}` advisory lock 下串行。
- **推进商机**：以"阶段仍是读到的那个"为条件先锁住商机（条件更新），并发的另一次推进返回 409 而不是悄悄覆盖；每次推进自动写一条"阶段变化"跟进记录（不能删除），并发布 `crm.deal_stage_changed`。编辑客户、联系人、商机都带 `expectedUpdatedAt` 检测冲突。
- **跟进记录**：电话、会议、邮件、备注，至少关联客户、联系人、商机中的一个；只关联商机或联系人时自动补上其所属客户，所以客户页能看到名下全部往来。所选客户、联系人必须与商机一致，联系人换到别的客户时自动解除它与原客户商机的关联。客户、联系人、商机的"最近往来时间"是冗余字段，记录跟进时用条件更新刷新、删除跟进时按剩余记录重算，不算编辑，不影响冲突检测。
- **自定义字段**：客户、联系人、商机各自最多 50 个字段，类型有文本、数字、日期、单选、多选、是否；字段有标识（小写字母开头，创建后不能改，智能体和工作流按 `customFields.<标识>` 读写）、名称、选项、新建时必填、说明和顺序。值以标识为键存在各实体的 `custom_fields`（jsonb）里，写入时按定义规范化：文本去首尾空白、数字接受 `1,200` 这样的写法、日期统一为 `yyyy-MM-dd`、选项不区分大小写地对齐到定义里的写法、多选去重，"是否"只存 `true`，空值不存；错误按 `customFields.<标识>` 逐项返回。新建时检查必填；编辑时不传 `customFields` 保持原值，传了就整体替换（动作里只传要改的字段，内部与原值合并，值为 null 表示清除）。字段配置在 `crm-fields:{tenant}` advisory lock 下串行，类型和标识不能改；删除字段或删掉某个选项时，用一条 SQL 从全部记录里清掉对应的值，不留下界面看不到的旧值。
- **导入**：客户和联系人可以从 CSV / TSV 或 Excel（第一个可见且有内容的工作表）导入，最多 10 MB、5000 行、100 列。先预览：读出表头和前几行示例，按名称和常见别名自动建议每列对应的字段（包括自定义字段）；确认对应关系后可以先"检查"（完整校验但不写入），再正式导入。客户按名称、联系人按邮箱判断是否已存在（不区分大小写），已存在时可选跳过、更新（只用非空单元格覆盖，标签取并集，自定义字段合并）或照样新建；同一文件里重复的行也报错（照样新建时除外）。负责人按邮箱或唯一的显示名匹配；联系人的所属客户按名称匹配，可以选择自动新建不存在的客户（客户有必填自定义字段时不允许）。有问题的行跳过并报告行号和原因（最多列出 200 行），其余行在一个事务里写入；同一空间的导入在 `crm-import:{tenant}` 锁下串行，同一份文件连点两次也不会导入两遍。导入不发布 `crm.*_created` 事件，避免一次导入触发成百上千次工作流；实时通道按实体类型各推一次。表格读取（`ITabularFileReader`）和知识库的文件提取共用上传读取、文本编码识别和 OpenXML 打开逻辑。
- **销售看板**：按阶段分列商机；进行中金额、按概率加权的预测金额、本月赢单金额按货币分别合计（不做汇率换算）；赢单、输单列只含最近 30 天结束的商机。合计在数据库里分组聚合，卡片数量有上限。
- **搜索**：名称、邮箱、电话等用 `ILIKE` 包含匹配，`pg_trgm` 的 GIN 索引让包含匹配也能走索引。应用层通过 `ITextMatcher` 表达"包含"，PostgreSQL 实现负责转义通配符并显式指定转义符，Application 层不依赖 Npgsql。
- **动作**（供对话、智能体、工作流、MCP 使用）：`crm.search`、`crm.get_company`、`crm.get_contact`、`crm.get_deal`、`crm.list_deals`、`crm.get_pipeline`、`crm.create_company`、`crm.update_company`、`crm.create_contact`、`crm.update_contact`、`crm.create_deal`、`crm.update_deal`、`crm.move_deal`、`crm.log_activity`、`crm.list_fields`（列出自定义字段及选项，供智能体在建档、修改前查看）。阶段按名称指定，找不到时错误里列出可选阶段；修改类动作只需传要改的字段，内部先读当前版本再带版本号提交。
- **事件**：`crm.company_created`、`crm.contact_created`、`crm.deal_created`、`crm.deal_stage_changed`、`crm.activity_logged`，载荷里带 `customFields`，工作流条件可以写 `trigger.company.customFields.region == '华东'`；例如"商机赢单（`trigger.to.kind == 'won'`）后自动建交付任务派给智能体"。
- **新空间初始化**：模块可以实现 `ITenantInitializer`，注册新空间时在同一事务里执行（CRM 用它写入默认阶段）；已有空间由迁移补齐。

## 进销存（ERP）

第二个业务模块，验证模块之间的依赖。模块键 `erp`，依赖 `crm`：订单的客户、联系人、商机和供应商直接用客户管理里的记录。权限 `erp.view`、`erp.sales`（销售订单）、`erp.purchase`（采购订单）、`erp.inventory`（产品、仓库、库存调整）；内置"成员"可查看和开销售订单，"只读"可查看，首席助理默认可查看、开销售和采购订单。

- **模块依赖**：模块用 `DependsOn` 声明依赖，`IModuleCatalog.ResolveEnabled` 计算实际生效的模块，依赖没启用的模块视为停用（权限、接口、动作、事件一并关闭）。启用时依赖必须已启用（409 `module.dependency_disabled`），停用时不能有已启用的模块依赖它（409 `module.required_by`），在 `modules:{tenant}` advisory lock 下判断。
- **数据**：产品（编码唯一、单位、分类、售价与参考采购价、是否管理库存、补货提醒线、在售或停售）、仓库（每个空间有且只有一个默认仓库，部分唯一索引保证）、库存（产品 × 仓库的现有和已预留数量与平均成本，可用 = 现有 − 已预留）、库存流水（每笔变动的数量、变动后结存和成本，关联订单和出入库单）、销售订单、采购订单（明细记录已交付和已退的数量）、出入库单（发货单、收货单、客户退货单、采购退货单，每次发货、收货、退货各一张，记录本次的数量、金额和成本）。订单明细、出入库单明细是从属集合，单独成表。订单号和单据号按空间连续编号（`SO-0001`、`PO-0001`、`SH-0001`、`GR-0001`、`SR-0001`、`PR-0001`），由 `tenant_sequences` 表的 `INSERT … ON CONFLICT DO UPDATE … RETURNING` 原子分配，随事务回滚。
- **库存一致性**：所有数量变化都经过 `IStockLedger`：一条带条件的 `UPDATE … RETURNING`（例如"现有 − 已预留 ≥ 本次数量"）同时完成检查和修改，不先读后写，所以并发下单不会超卖；库存行第一次用到时 `INSERT … ON CONFLICT DO NOTHING` 补出来。一次操作涉及多行时按产品、仓库排序加锁，避免死锁。"是否管理库存"决定确认、发货、收货、调整动不动库存：这些操作先对产品行加共享锁再读取它，修改产品时对产品行加排他锁，切换前的检查（有没有已确认未发货的订单、还有没有库存）不会和它们交错。
- **金额与精度**：数量、单价最多 4 位小数（与 `numeric(18,4)` 一致）；行金额和订单合计在保存前检查不超过 `numeric(18,2)` 能存的范围，超出时返回 400。
- **销售订单**：草稿 → 已确认（按明细预留库存，任一产品不够则整单不确认，错误里列出全部缺货）→ 部分发货 → 已发货。每次发货可以只发一部分（不填明细时发出剩下的全部），扣减现有和预留，写一张发货单和出库流水；全部发完变为已发货，也可以在部分发货时"结束发货"，释放剩下的预留。草稿、已确认可以取消（已确认的释放预留），发过货的不能取消。状态流转以"状态仍是读到的那个"为条件先锁住订单，并发的重复确认、发货返回 409。从商机生成时带出客户、联系人和货币，商机必须属于所选客户；单价默认取产品售价，货币不同时必须手填。
- **采购订单**：草稿 → 已下单 → 部分到货 → 已收货。可以分批收货，每次一张收货单；部分到货时可以"结束收货"。草稿、已下单可以取消。供应商是客户管理里的公司。
- **退货**：部分发货或已发货的销售订单可以登记客户退货（每个产品最多退已发数量减已退数量），货退回所选仓库；已收货的采购订单可以退给供应商，只能动用可用数量，已预留给销售订单的不能退（409）。每次退货一张退货单，订单的发货、收货金额和毛利按退货冲减。
- **成本核算**：每个仓库按移动加权平均计算成本。入库时在同一条条件 `UPDATE` 里按"（原数量 × 原成本 + 本次数量 × 本次单价）/ 新数量"重算平均成本，出库按当时的平均成本计价，平均成本不变；只锁库存行，不碰产品行，所以不会和产品上的共享锁形成死锁。采购收货按采购单价入库，采购货币与产品货币不同时（暂不换算汇率）按产品的参考采购价；调拨时成本随货走；调整库存可以填单位成本，不填时沿用平均成本，仓库还没有成本时用参考采购价；客户退货按这张订单发货时的净成本入库，退给供应商按当前平均成本出库。成本都以产品的货币计，还有库存时不能改产品货币（409 `erp_product.currency_locked`）。销售订单的成本和毛利由它的出入库单汇总，有产品的货币与订单不同时毛利不计算。分批发货时每批金额按"累计数量的金额 − 已发数量的金额"计算，分几次发完加起来正好等于整行金额。升级前已发货、已收货的订单在迁移时整单补一张发货单或收货单，历史成本按参考采购价估算。
- **库存调整与调拨**：按增减数量，或按盘点后的实际数量调整（锁住库存行后计算差额）；调拨在两个仓库之间移动可用数量。不管理库存的产品（服务等）下单、发货不检查也不记录数量。库存列表按"管库存的产品 × 仓库"列出，没有记录的组合按 0 计，新产品不会漏掉。
- **补货提醒**：发货、调整、调拨、退给供应商让产品的可用总数从提醒线以上降到提醒线及以下时，发布一次 `erp.stock_low`。
- **概况与指标**：概况显示本月发货（扣除退货）、本月毛利、待发货（已确认和部分发货的订单与未发金额）、本月采购入库、库存金额和库存预警；经营分析的 `erp.sales_shipped`、`erp.gross_profit`、`erp.purchases_received` 都由出入库单按单据时间统计，与概况口径一致。订单列表可以用 `pending=true` 只看还没发完或收完的订单。
- **动作**：`erp.search_products`、`erp.get_product_stock`、`erp.get_summary`、`erp.create_product`、`erp.adjust_stock`、`erp.list_sales_orders`、`erp.get_sales_order`、`erp.create_sales_order`（可以直接确认）、`erp.confirm_sales_order`、`erp.ship_sales_order`（可以按产品编码只发一部分）、`erp.close_sales_order`、`erp.return_sales_order`、`erp.cancel_sales_order`、`erp.list_purchase_orders`、`erp.create_purchase_order`、`erp.place_purchase_order`、`erp.receive_purchase_order`（可以分批）、`erp.close_purchase_order`、`erp.return_purchase_order`。产品按编码、仓库按名称、订单按单号指定，找不到时错误里提示怎么查（解析直接查当前空间，不要求额外的查看权限）；取消销售订单、结束发货或收货、退货、向供应商下单、调整库存对智能体要求人工审批。
- **事件**：`erp.sales_order_confirmed`、`erp.sales_order_shipped`、`erp.purchase_order_received`（分批时每批一次，载荷带本次的出入库单）、`erp.sales_order_returned`、`erp.purchase_order_returned`、`erp.stock_low`，例如"库存低于提醒线时让智能体起草采购单，交给人确认下单"。

## 项目管理

第三个业务模块，把已有的任务组织成项目。模块键 `projects`，依赖 `agents`（任务属于智能体团队模块）。权限 `projects.view`、`projects.manage`；内置"成员"可管理、"只读"可查看，首席助理默认可管理，已有空间和智能体由迁移补齐。

- **数据**：项目（名称在空间内不区分大小写唯一、目标、状态、负责人、开始和目标日期）、里程碑（有序、截止日期、完成时间）、项目成员（成员或智能体，附职责说明）。任务新增可选的 `projectId`、`milestoneId` 和截止日期；子任务不指定时沿用父任务的项目和里程碑。负责人可以是成员或智能体，设为负责人时自动成为项目成员，负责人不能被移出项目。
- **状态**：规划中 → 进行中 ⇄ 暂停 → 已完成 / 已取消。还有未关闭任务时不能完成项目（409 `project.open_tasks`），里程碑同理（409 `project_milestone.open_tasks`）；已完成或已取消的项目不能再加任务和改里程碑（409 `project.closed`），已完成的里程碑不能再加任务。删除项目时任务保留，只是解除归属。
- **进度**：项目和里程碑的进度都由所属任务实时统计（总数、完成、进行中、阻塞、逾期、完成百分比），已取消的任务不计入；在数据库里分组聚合，列表一次查询算完。
- **并发**：任务加入项目、完成项目或里程碑、改里程碑、调整负责人都在 `project:{id}` advisory lock 下判断，"完成里程碑"和"往里程碑加任务"不会交错（有测试在去掉锁时稳定复现竞争）；项目重名检查在 `project-names:{tenant}` 锁下进行。编辑项目带 `expectedUpdatedAt` 检测冲突。
- **与智能体协作**：负责人是智能体时，被设为负责人、项目里的任务被阻塞、某个里程碑或整个项目的任务全部关闭时会唤醒它（操作者就是负责人本人或项目已关闭时不唤醒）。智能体的提示词里列出它负责的项目和进度，当前任务附带所属项目、里程碑、项目目标和截止日期（逾期会注明）。
- **任务依赖**：任务有可选的开始日期，可以声明前置任务（完成到开始：前置任务都关闭——完成或取消——后才能开始，可以跨项目），每个任务最多 50 个。不能依赖自己、不能重复，加依赖前用递归 CTE 检查是否会形成循环（409 `work_item_dependency.cycle`）；检查和写入在 `task-dependencies:{tenant}` advisory lock 下进行，两个人同时加相反方向的依赖时只有一个成功（有测试在去掉锁时稳定复现）。还有未关闭前置任务的任务不会被智能体领取（领取的条件更新里直接排除），指派给智能体时也先不唤醒；最后一个前置任务关闭或依赖被删掉时，以「前置任务完成」为来源唤醒负责的智能体。提示词里注明「等待前置任务 T-a 关闭后才能开始」，当前任务列出前置和后续任务。
- **排期与甘特图**：`GET /api/projects/{id}/schedule` 返回项目里未取消的任务（最多 500 个，按里程碑和开始日期排序）、项目内的依赖、起止范围、未排期数量和冲突。只有截止日期或只有开始日期的任务按那一天算，后续任务可以在前置任务截止当天开始，早于这一天且两者都未关闭时算冲突。关键路径做一次反向推导：没有后续任务的以未关闭任务里最晚的截止日期为最晚完成，往前推出每个任务的最晚开始，余量不超过零的未关闭任务在关键路径上。`PUT /api/work-items/{id}/schedule` 改起止日期（带 `expectedUpdatedAt`），可选顺延后续任务：按拓扑顺序只推动因这次调整而冲突的后续任务（开始和截止一起往后挪，关闭的、没有日期的不动，不会往前拉），每个后续任务用带原日期条件的 `ExecuteUpdate` 写入，期间被改过就整体回滚（409 `work_item.modified`）。Web 端甘特图按日、周、月缩放，拖动时间条整体移动、拖两端改开始或截止，也可以用方向键；未排期的任务在它那一行双击安排；依赖画成折线箭头，冲突为红色虚线，关键路径加红框；全部是 HTML 和 SVG，没有引入图表库。
- **动作**：`projects.list`、`projects.get`、`projects.get_schedule`（排期、冲突和关键路径）、`projects.create`（可以一次带上里程碑，同一事务创建，所以在工作流步骤里也能用）、`projects.update`、`projects.add_milestone`、`projects.complete_milestone`、`projects.add_member`，以及任务侧的 `tasks.schedule`（调整任务的项目、里程碑、开始和截止日期，可选顺延后续任务）、`tasks.add_dependency`、`tasks.remove_dependency`；`tasks.create` 可以带开始日期和前置任务。项目、里程碑都可以按名称指定，解析直接查当前空间。
- **事件**：`projects.project_created`、`projects.project_status_changed`、`projects.milestone_completed`，例如"项目完成后让智能体写一份复盘文档"。

## 经营分析

模块键 `analytics`（默认启用），权限 `analytics.view`（看概览、报表、查指标）和 `analytics.manage`（保存、排序、删除报表）。内置"成员"两项都有、"只读"可查看，首席助理和新智能体默认可查看，已有空间由迁移补齐。

- **指标**：各业务模块实现 `IPlatformMetric`（与平台动作一样按程序集扫描注册），只负责按天取出原始值：投影成 `MetricRow`（时间、分组、货币、数值、权重），再统一用 `ByDayAsync` 在数据库里按 `date_trunc('day', at AT TIME ZONE 时区)` 分组汇总。没写的成员自动补默认值，每个指标一条查询。现有指标：新增商机、赢单金额与数量、赢率、跟进次数、发货金额、采购入库金额、新建与完成任务、智能体执行次数与成功率、AI 花费与令牌、工作流运行次数与成功率。
- **口径**：区间、分桶、拆分、对比统一由 `AnalyticsEngine` 处理，指标之间保持一致。日期都是空间时区里的日期，区间首尾都包含；按周从周一开始。金额按货币分开统计，默认取区间内金额最多的货币，不做汇率换算。比率类指标（赢率、成功率）的数值是分子、权重是分母，合计是整个区间的比率而不是各天相加。拆分取前 N 组，其余合并为"其他"；维度值换成名称时只查当前空间，找不到的显示"已删除"。
- **环比**：本月对上月同期，上月对再上一个整月（月末对月末），本季度对上季度同期，今年和近 12 个月对前一年同期，其他区间对紧挨着的等长区间。单次查询的跨度有上限（按天 366 天、按周 731 天、按月 1830 天）。
- **权限**：查指标除了 `analytics.view`，还要有指标所属模块的查看权限且模块已启用（看赢单要有 `crm.view`，看 AI 花费要有 `platform.usage.view`）；拆分维度也可以要求额外权限，例如按项目拆分任务要能看项目。报表只能引用保存者自己看得到的指标和维度。
- **概览**：关键指标及环比、销售漏斗、库存预警、项目进度、智能体工作量，各部分按模块和权限出现。
- **报表**：保存的是指标、拆分、货币、快捷区间、粒度和图表类型，每次打开都按当天重新计算；空间内共享，可以排序，编辑带 `expectedUpdatedAt` 检测冲突。
- **空间时区**：空间有 IANA 时区（注册时取浏览器或手机的时区，设置里可改，Windows 时区名会被换成 IANA 名称），经营分析按它分天，智能体唤醒消息和对话的系统提示里也写明当地日期、星期和时区，模型理解"今天""本月"不会差一天。时区换算依赖 ICU，所以后端不开启全球化固定模式，格式化和比较一律显式指定区域性。
- **动作**：`analytics.list_metrics`、`analytics.query`（不指定粒度时按区间长短自动选，返回合计、环比、趋势和拆分排名）、`analytics.get_overview`，都是只读，对话和智能体可以直接回答"这个月赢单多少""近 30 天谁完成的任务最多"。
- **客户端**：Web 有概览、报表和自由分析三页，图表是自己画的 SVG（折线、堆叠柱状、悬停提示），明细表可以导出 CSV；业务数据变化时经营分析的查询在实时通道里限流，最多每 10 秒刷新一次。手机"我的"里有经营分析概览，下拉刷新。

## 对话

对话是用户与平台的直接入口：用户消息和模型回复（含工具调用与结果）按序存储在 `conversation_messages`（jsonb）。每一轮在当前用户的身份与权限下调用平台动作，所以对话里能做的事和界面上完全一致。客户端可以用 SSE（`POST /api/conversations/{id}/messages`）或 SignalR 的 `StreamChat` 接收流式事件。

同一对话同时只跑一轮（PostgreSQL advisory lock，跨实例生效），上一轮没结束时新消息返回 `conversation.busy`。带给模型的历史是最近 60 条且不超过约 12 万字符，并从一条用户消息开始，长对话不会撑爆上下文窗口。

## 知识与记忆

- **文档** 保存时同步切成片段（按段落累积，超长段落按句子切，每段带上 Markdown 标题路径，相邻片段少量重叠），立即可以按关键词检索；**记忆** 是一条条短事实，各自是一个片段。两者存在同一张 `knowledge_chunks` 表里，检索一次覆盖。
- **关键词检索** 不依赖数据库分词插件：应用内分词（中日韩文字切成二元组，其他文字按词，全角折叠为半角），存成生成列 `tsvector` + GIN 索引。
- **向量检索**：后台索引器批量向量化新片段，写入 `vector(1024)` 列（HNSW 余弦索引）。任何模型的输出都统一到 1024 维（补零或按 Matryoshka 截断，再归一化）；更换模型后旧向量自动逐批重建。没有配置向量模型时用离线演示向量（特征哈希）。
- **混合排序**：向量近邻与关键词各取候选，按倒数排名融合（RRF，k = 60）；向量候选有距离门槛，过滤掉不相关的近邻。HNSW 开启迭代扫描，带过滤条件时也能凑满候选。
- **可见性**：文档全空间可见；记忆分共享、成员私有、智能体私有，检索时按当前操作者过滤，`memory.manage` 可以查看全部。原生 SQL 绕过了 EF 过滤器，所以租户和可见性条件在检索 SQL 里显式写出。
- 同一归属下内容相同的记忆只保留一条；智能体记下的记忆会关联到当时的执行和任务，便于追溯。
- **上传文件**：`POST /api/knowledge/files/extract`（multipart，最大 20 MB，需要 `knowledge.manage`）把文件转成 Markdown 草稿，确认后照常保存成文档，不会直接入库。按扩展名选择解析器：PDF 用 PdfPig（按版面切块、按阅读顺序排列，字号明显大于正文的短行变成标题，去掉每页重复的页眉页脚和页码；扫描件没有文字层时提示先做文字识别，加密文件给出明确提示）；Word、Excel、PowerPoint 用 DocumentFormat.OpenXml（标题样式和大纲级别变成 Markdown 标题，列表、表格保留结构，Excel 每个可见工作表一张表并按单元格格式显示日期，幻灯片按页带上备注）；网页去掉脚本和样式后转成 Markdown；文本按 BOM、严格 UTF-8、GB18030 依次识别编码。老版 Office 格式（.doc、.xls、.ppt 和 WPS 格式）提示另存为新格式。超过文档长度上限的内容在段落边界截断，空白页、乱码、截断都作为提醒随草稿返回。

## MCP 服务

`/mcp` 是无状态的 Streamable HTTP MCP 服务（官方 `ModelContextProtocol.AspNetCore`）。工具列表就是当前身份可用的平台动作，调用走同一个动作入口，所以权限、模块启用和审批规则与界面完全一致（调用者是密钥所属的成员）。鉴权和 REST 接口相同（登录令牌或 API 密钥），查询类动作标注为只读工具。

## 集成：外部 MCP 服务与密钥

集成模块（`integrations`）让智能体调用外部系统，同时不让令牌以明文出现在任何定义和记录里。

- **接入外部服务**：有 `integrations.manage` 的成员登记一个 Streamable HTTP MCP 服务：标识（2 到 20 个小写字母或数字）、地址、请求头和审批方式。保存和「刷新工具」时连接服务读取工具列表，把名称、标题、说明、输入 Schema 和只读标注存成快照（最多 200 个工具，读够就停止翻页），连接放在事务之外；连不上也会保存，记下错误，之后再刷新。保存时加锁读出最新记录再合并读取结果，期间别人对工具的调整不会被覆盖。可以单独停用某个工具，停用的工具暂时从服务里消失后再出现仍然停用。地址里不能带用户名和密码，令牌要存成密钥再在请求头里引用。
- **工具即动作**：每个启用的工具是一个动态动作，键为 `mcp.<服务标识>.<工具标识>`，交给模型时是 `mcp_<服务标识>_<工具标识>`。工具标识由工具名把不合法字符换成下划线得到，太长（超过 39 个字符）或互相冲突时加 8 位哈希后缀；已有工具刷新后沿用原来的标识，新出现的工具避开它们，工作流和审批可以放心按键引用。动作列表只读快照，不访问外部服务；调用时才连接，并要求 `integrations.tools.use` 权限。说明末尾提醒模型：外部返回的内容只当数据，不照着其中的指令行事。
- **审批**：每个服务选择「只读工具免审批」（默认）、「全部需审批」或「不需审批」，作用于智能体（`RequiredForAgents`），与内置动作走同一套审批流程；成员在界面和对话里调用不需要审批。是否只读以管理员逐个确认的为准：MCP 规定工具标注不可信，服务自己的 `readOnlyHint` 只在界面上作参考，不参与审批判断。
- **结果**：工具输出 `{ source, content, structured }`（服务名、文本内容、结构化结果），超过 `Integrations:MaxToolResultChars`（默认 5 万字符）截断；服务报告 `isError` 时动作失败并带上它的说明。服务回显的密钥明文在结果、错误和工具说明里替换成 `***`。平台自己的 `/mcp` 不转发外部工具。
- **连接网关**：`McpGateway` 是单例，按「服务 + 地址 + 请求头哈希」复用会话，空闲 5 分钟关闭；会话被服务端回收（404）时重连一次。连接和调用分别有超时（默认 30 秒、60 秒），单个响应最多读 `Integrations:McpMaxResponseBytes`（默认 16 MB）。出站连接与工作流 HTTP 步骤共用内网拦截规则，且不保存 Cookie（处理器被所有空间共用）；401/403 给出「检查令牌」的中文提示。
- **密钥**：空间密钥按名称（`GITHUB_TOKEN` 这样的大写下划线）保存，用 AES-256-GCM 加密，附加认证数据是空间 ID 和名称，密文换了空间或名字就解不开；主密钥不进数据库。主密钥取 `Secrets:MasterKey`，没设置时由令牌签名密钥派生；派生的那把始终参与解密，`Secrets:PreviousMasterKeys` 放轮换前的旧主密钥，密文带主密钥指纹，按指纹挑选。接口从不返回明文，只能更换。
- **引用密钥**：只能在外部服务的请求头和工作流 HTTP 步骤的请求头里写 `{{ secrets.名称 }}`，别处出现会在保存时被拒绝。渲染时先切出密钥引用再渲染其余模板，所以上下文里的数据不会被当成引用解析。引用密钥要求 `integrations.secrets.use`（能引用就能把密钥发往任意地址，等同于能读取）：工作流在保存时和每次运行时检查负责人；外部服务在新建、改地址或新增引用时检查保存者，只改名称、审批等其他设置不要求。HTTP 步骤的响应和错误里回显的密钥明文替换成 `***` 再记录。被外部服务或工作流引用的密钥、被工作流引用的服务不能删除，服务标识也不能改；保存引用和删除密钥在事务里争用同一把锁，删除不会漏掉刚保存的引用。

## 实时通道

写操作提交后发布 **实体变更**（agent、work_item、run、approval、conversation、module、knowledge_document、memory、workflow、workflow_run、tenant、mcp_server、tenant_secret，以及各业务模块的实体，如 project、analytics_report），SignalR 按租户分组推送；客户端据此让对应查询失效重取，三端都不轮询。查看某次执行时可订阅该执行的分组，接收逐字输出和新事件；客户端会在断线重连后自动重新订阅，并把当前查询全部重取一次补上断线期间的变化。连接的启动与断开按调用顺序串行执行（切换空间时不会卡在断开中），首次连接失败会按退避节奏继续重试。

编辑类接口带上读取时的 `updatedAt`（例如 `UpdateWorkItemRequest.expectedUpdatedAt`），期间被别人或智能体改过就返回 409，而不是用旧数据覆盖。成员被停用、移除或角色权限变化后，本实例的权限缓存在提交后立即清除。

## 模型网关

所有模型统一为 `Microsoft.Extensions.AI` 的 `IChatClient`：

- `anthropic`：官方 Anthropic .NET SDK，默认模型 `claude-opus-5-5`。
- `openai`：OpenAI 及任何兼容端点（`BaseUrl` 指向即可，如本地 Ollama）。
- `demo`：未配置密钥时的内置演示模型，会按真实流程调用工具，便于本地体验和测试。

客户端按（供应商, 模型）缓存；花费按内置价格表或配置的 `Ai:Pricing` 估算。

## 客户端

- **Web**：Next.js App Router + shadcn/ui；TanStack Query 管理服务端状态，查询键集中定义，实时变更映射到查询失效。可通过 `NEXT_OUTPUT=export` 静态导出。
- **桌面**：Tauri 2 只做原生外壳，加载 Web 静态导出；单实例、窗口状态记忆、外链用系统浏览器打开；CSP 限制脚本只能来自应用本身。
- **移动**：Expo Router；令牌存系统安全存储；对话用 `expo/fetch` 读流，任务与审批通过 SignalR 实时刷新；知识页可以检索文档和记忆；“我的”里可以查看、启停和手动运行工作流；“客户”页可以查商机、客户和联系人，一键拨号或发邮件，推进商机、随手记录跟进；“我的”里还能查看项目进度和排期一览（关键路径、冲突）、完成或重新打开里程碑，任务详情列出前置和后续任务，以及经营分析概览。
- 三端共用 `@ainative/api-client` 里的 `sessionCan`，按与后端相同的通配规则决定显示哪些入口。

## 部署

生产镜像只有一个应用容器：后端在同一个站点提供接口、实时通道、MCP 和 Web 工作台的静态导出（`wwwroot`）。页面地址映射到导出的文件（`/analytics` → `analytics.html`），找不到的页面返回导出的 404 页，`/api`、`/hubs`、`/mcp`、`/health` 下的路径不受影响；静态资源在构建时预压缩，按 `Accept-Encoding` 发送 br 或 gzip 版本，带哈希的文件永久缓存。流式响应带 `X-Accel-Buffering: no`，经过 nginx 也能逐字到达。

开发环境以外，启动时检查令牌签名密钥（缺失、太短或沿用仓库里的开发密钥都拒绝启动）；`Auth:AllowRegistration` 可以关闭自助注册，之后由管理员添加成员。部署步骤与配置项见 [deployment.md](deployment.md)。
